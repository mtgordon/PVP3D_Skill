# Mistakes made in the reference session, and how they were caught/fixed

Quick-reference table, roughly chronological. Full detail on the FEBio-syntax
ones is in `febio-xml-format.md`; this file is for the higher-level process
mistakes that aren't specific to XML syntax.

| Mistake | How it was caught | Fix / lesson |
|---|---|---|
| Replaced a "wrong but stabilizing" blanket boundary condition with anatomically-correct-but-narrower ones, and the model went from failing at a moderate load fraction to failing instantly at zero load. | Ran the "corrected" file before declaring victory -- always run every change, don't assume a more-correct-looking BC is also more-stable. | The old, imprecise BC was accidentally providing numerical stabilization the precise one didn't. When "more correct" makes things *less* stable, that's real information: something else in the model was silently depending on the imprecision. Isolate by testing the old BC + new BC together (additively) before assuming the new one is simply wrong. |
| Assumed a contact's proximity tolerance change (loosening it so it would actually find pairs) was safe on its own. | The same "instant failure at zero load" symptom recurred with the *old* BC scheme too, once the tolerance was loosened -- proved it was a second, independent variable. | Change one variable at a time even when two changes seem related (BC scheme and contact tolerance both touch "how is this part attached"). Conflating them wastes a whole debugging cycle figuring out which one actually mattered. |
| Built a "phantom" facet-only surface for a tie, using nodes with zero material stiffness of their own, and didn't anticipate that the tie's penalty force would be the *only* thing resisting those nodes' motion. | Isolation test: disabled the tie (kept everything else), confirmed the rest of the new geometry was stable alone; re-enabling any single one of several new ties reproduced the same order-of-magnitude blowup, at a load fraction so small the ramp-in curve was barely engaged. | A node with no stiffness contribution of its own, referenced only by a contact/tie, is a near-singular DOF. See `febio-xml-format.md` gotcha 8. The attempted fix (linking it to a real node with a small spring) was not confirmed working before time ran out -- don't assume that class of fix is correct without re-testing at small scale first (a single spring + single tied phantom node in a minimal file). |
| Inserted large blocks of new content (new nodes) in the middle of a big XML file, positionally near the *old* content being replaced, without checking whether that position was valid for a hidden ordering rule. | The parse error's line number pointed at a location far from the actual inserted content and referenced a node ID that looked perfectly valid in isolation -- required comparing that ID against the highest ID declared earlier in the file to spot the pattern. | Don't assume "logically related" content belongs at the same physical file location as what it's replacing. FEBio's node-ID monotonicity rule (`febio-xml-format.md` gotcha 1) meant new high-numbered nodes had to move to the very end of the mesh's node declarations, and everything referencing them had to move with them. |
| Guessed at FEBio XML syntax for an unfamiliar construct (a bare-node `<Surface>`, matching Abaqus's `type=NODE`) and wrote it directly into the real multi-megabyte model file. | The failure was a generic "unrecognized tag" with no further detail, and required stripping the real file down to guess-and-check, which is slow on a huge file. | Always verify unfamiliar syntax in a small throwaway file first (`febio-xml-format.md` gotcha 6). It takes seconds per iteration instead of the much longer edit-run-diagnose cycle on the real file, and the error messages are unambiguous when there's nothing else in the file to confuse the picture. |
| Tried to read the bundled FEBio manual PDF for authoritative parameter documentation. | `pdftoppm is not installed` -- the PDF-rendering dependency needed by the file-reading tool wasn't present, and there was no network access to fetch documentation online either. | When official docs aren't reachable, the installed program's own compiled binaries are a legitimate fallback: extract printable ASCII strings from the relevant `.dll`/`.exe` and grep for keyword-shaped substrings -- compiled-in factory-registration strings are usually the literal XML type names the parser accepts. See `febio-xml-format.md` gotcha 7. |
| Assumed "more solver patience" (smaller minimum step size, more retries) would help push through a difficult point, based on general FE intuition. | Directly tested it: a finer step-size configuration performed *worse* (reached a smaller fraction of the load) than a coarser one on the same model, despite taking many more total steps. | Solver-robustness settings are not monotonic in the way intuition suggests. Always A/B test a proposed robustness improvement against the current best baseline rather than assuming a "should help" change actually does. This generalizes: nearly every fix attempted in this session was tested empirically rather than trusted on reasoning alone, and several confident-sounding hypotheses (this one included) turned out backwards. |
| When re-introducing a previously-removed contact alongside new geometry, forgot to re-apply a load-curve ramp that had already been established as necessary for that exact contact in an earlier attempt. | The new variant failed identically to the very first (pre-ramp) attempt at that contact -- recognized the repeated failure signature rather than treating it as a new mystery. | When recombining previously-tested pieces into a new variant, explicitly re-check that every previously-necessary mitigation (ramps, tolerances, solver settings) is still present in the new file -- it's easy to drop one silently when copying/rebuilding a file from an earlier stage rather than the most recent one. |
| Nearly proceeded on the assumption that a `<discrete>` binding's `discrete_set` reference was broken, when testing it in total isolation (no material, no elements at all in the file). | The exact same markup worked once a single trivial, unrelated material + element domain was added anywhere else in the same test file. | A "minimal" test file can be *too* minimal and trip an unrelated initialization requirement, producing a misleading error that looks like it's about the construct under test. When a minimal repro fails in a confusing way, try adding back one trivial "normal" ingredient before concluding the construct itself is broken. |
| Wrote several files (via a file-write tool) to a location that turned out to be a managed/synced skills directory (recognizable by a sibling `manifest.json` and a set of standard bundled skill names alongside the new content), got "created successfully" confirmation for each, then found the entire folder deleted on a later check -- apparently pruned by a reconciliation process for not being in the manifest. | A plain directory listing from an independent tool, done specifically because the user flagged the risk of a synced location, showed the folder was simply gone -- no error had been reported at write or delete time. | Don't trust a tool's success confirmation alone for anything that must persist and be read back later (a skill file, a deliverable meant to outlive the current turn) -- verify immediately with an independent listing, and *especially* avoid writing anything meant to be durable into a directory that sits next to a `manifest.json` or otherwise looks like it's under automated management, even if its path doesn't literally contain the word "synced." Prefer an explicit, plain user-owned directory (e.g. under the tool's own dotfile config directory, not a path with session/conversation-scoped GUID segments) for anything that needs to survive past the current session. |
| A Perl classification script picked "which target a node ties to" via `my ($x) = grep {...} keys %hash;` -- the *same* script, run twice on *identical* input, gave a different answer for a node that legitimately bordered two different targets. | Ran the exact same command three times in a row specifically to check reproducibility (prompted by a downstream result looking inconsistent between builds), and got two different classifications across the three runs. | Perl (5.18+) randomizes hash key iteration order per-process by default, as a security feature -- `keys %hash` (and anything downstream of it, like `grep`/first-match-wins logic) is not deterministic across runs unless explicitly sorted. This silently varied a geometric classification across every rebuild of a multi-stage pipeline that happened to call this code, confounding comparisons between builds that were assumed to differ *only* in one intentionally-changed parameter. Fix: `sort` before taking a first/arbitrary match from any hash-derived list whose order could affect output (`my ($x) = sort grep {...} keys %hash;`). Generalizes beyond this project: any Perl (or similarly hash-randomizing language/runtime) script whose output should be exactly reproducible between runs needs an explicit, deterministic tie-break wherever it currently relies on hash iteration order, even where that reliance isn't obvious from reading the code. |
| A splice/filter script used two different "skip until a closing tag" states (an Elements-block skip and a ShellDomain-block skip) with a shared, non-specific early check (`next if $skip;`) placed *before* the more specific check that would have reset the second state -- once the ShellDomain skip state was entered, the generic check intercepted every subsequent line before the specific close-tag check ever ran, so the file was silently truncated from that point to the end. | The very next run's output file was hundreds of lines shorter than the input for no apparent structural reason, and the FEBio parser error was a generic "unrecognized tag" far past where the actual bug was. | Overlapping/ambiguous multi-state skip logic in a text-splicing script is a real bug class, not just a style nitpick -- a later, more general check can silently shadow an earlier, more specific one. Prefer a single "what closing tag am I currently waiting for" state variable over multiple independent boolean/numeric skip flags whose check-order matters; it makes exactly one thing true at a time and removes the possibility of one state's catch-all swallowing lines meant for another state's own close-tag detection. |
| Wrote a postfix `for` across what looked like one multi-statement accumulator line: `$cx+=$nx{$_}; $cy+=$ny{$_}; $cz+=$nz{$_} for @n;` intending to accumulate all three coordinate sums over the loop. | The computed centroid was visibly wrong (two of the three coordinates came out using an uninitialized `$_`, triggering "Use of uninitialized value" warnings) once the result was checked against an independent calculation. | Perl's postfix `for`/`foreach` modifier binds to exactly the *one* statement immediately before it, not to a whole semicolon-separated sequence of statements on the same line -- only the last statement (`$cz+=...`) actually executed once per loop iteration; the earlier two ran exactly once total, with `$_` undefined outside the loop. Use an explicit block form (`for my $x (@list) { stmt1; stmt2; stmt3; }`) whenever more than one statement needs to repeat per iteration; reserve postfix `for` for genuinely single-statement loop bodies only. |
| Took the converter's version of a tie (LA_ICM-only primary surface, phantom-ribbon secondary) as the source's intent, and tuned it for days. | Resolved the Abaqus `*Tie` into actual node pairs: the slave surface was every element of the muscle, and 82-84 LA nodes per side were tied along the arcus. Most of them were in regions the FEBio contact could never reach. | Resolve source constraints into concrete node pairs before tuning a converted version of them (`abaqus-inp-format.md`, "Resolve every `*Tie`"). Reproduce node-to-node ties exactly with linear constraints (`febio-xml-format.md` gotcha 18) rather than approximating them with a proximity contact. |
| Assumed `tied-node-on-facet` preserves the initial offset, like Abaqus `adjust=no`. | A 20-line model with a 0.5 gap and no load diverged on iteration 2 after moving every node the full gap. | It closes gaps (`febio-xml-format.md` gotcha 17). This explains "huge INITIAL displacement when a tie engages" and the `max_distance` knife-edge. Use `node_reloc=1` or linear constraints. |
| Spent a batch of runs on physics-level fixes (Abaqus-consistent bulk modulus, three-field shells, a thinner membrane-equivalent shell, implicit dynamics) for a thick muscle shell that kept failing in the same elements. | Computed the failing elements' *reference* geometry through the thickness: with averaged nodal normals, 6 were already face-inverted at rest. They had passed every mid-surface quality check. | When the same elements fail in every variant, check their undeformed geometry (including shell thickness) first. `shell_normal_nodal=0` fixed what no material/solver change could (`febio-xml-format.md` gotcha 19, `geometry-cross-referencing.md` Rule 11). |
| Treated the "no-LA" baseline's supports as trustworthy because that model ran furthest. | A per-BC audit of active-versus-declared nodes across versions: two supports had pinned 0 live nodes since a remesh gave the fan nodes new IDs. | Mesh surgery can silently orphan BCs. Audit after every remesh or re-export (`scripts/bc_audit.py`, Rule 12). "The baseline runs" does not mean "the baseline is right". |
| A previous version of this skill told readers to assign instance-less assembly `*Nset`s to a neighbouring part, and documented `*Connector Elasticity` rows as `displacement, force`. | Checked against the `.inp`: 79 assembly-level `*Node` reference points exist, and connector tables share a displacement grid in column 2 while column 1 scales with stiffness. | Instance-less sets are assembly reference nodes, and connector tables are force-first. Both are now corrected in `abaqus-inp-format.md`. Verify skill guidance against the source file before acting on it, especially guidance that was inferred rather than tested. |
| Kept only the fixes that helped individually. | A shell fix alone reached 0.20, a coupling fix alone 0.20-0.27, and both together 0.56 (the model's shared wall). | Two independent defects each mask the other's fix. If isolated fixes disappoint, test combinations before discarding either. |
| Wrote a UTF-8 file with Python's default `open(p, 'w')` on Windows (cp1252). The encode error on a non-ASCII character fired *after* `open` had already truncated the file, so the draft was lost. | The file was 0 bytes on the next listing. | On Windows always pass `encoding='utf-8'` (and `newline=''` to keep line endings). Never rewrite a file you can't regenerate without a backup. Deeply nested scratch paths also exceed MAX_PATH (260) and make Python fail with "No such file"; work in a short path. |
| Spent an attempt fixing everything else (contacts, shells, connectors) while a model kept failing at the same load fraction it had failed at for several unrelated variants -- assumed a material/contact/mesh cause because the run converged cleanly for a long stretch first. | Grepped every Abaqus `*Boundary` set name against FEBio's `<Boundary>` block (`node_set=` attributes), not just against `<NodeSet>` declarations. One Abaqus `XSYMM` set had a correctly-named, correctly-populated FEBio `<NodeSet>` that no `<bc>` ever referenced -- the constraint itself was never written, and low-stiffness ground springs stood in for it well enough that nothing looked obviously wrong. | A silently-dropped BC can produce a graceful-looking failure indistinguishable from a real physical limit -- a `<NodeSet>` existing is necessary but not sufficient for its BC to be applied. When a wall persists across every unrelated fix, re-audit every source `*Boundary` against the target's actual `<bc>` usage before trusting the model's own convergence behavior to point at the cause (`abaqus-inp-format.md`). |
| Trusted `scripts/shell_pinch_check.py`'s result (1 Gauss-point-inverted element) as a clean bill of health for a thick shell that kept failing at the same wall no matter what else changed. | Re-derived the offset geometry from the FEBio User Manual: FEBio 4's default shell places nodes at the TOP face and extends a full thickness along -normal, not +-t/2 about a mid-surface as the script assumed. Re-running with the corrected offsets found 86 Gauss-point-inverted elements, not 1. | A diagnostic script's own geometric assumptions have to match the solver convention actually in force (here, `<shell_formulation>` in `<Control>`), not a superficially similar one carried over from an earlier FEBio version or a different tool. A tool running without error and returning "looks fine" is not the same as the tool being right -- re-derive from the manual when a persistent symptom doesn't match a clean result. Fixed in `scripts/shell_pinch_check.py`, which now auto-detects the convention. |
| Refit an Abaqus Marlow material as a 1-term Ogden that matched the uniaxial test data to about 10 %, and treated the conversion as done. Later, "the LA bulges too much" was blamed on the source setup because the supports matched. | Compared the two laws outside uniaxial tension. Marlow is I1-only, so the same data make it 2.1x stiffer at 20 % equibiaxial stretch and 2.9x at 40 %. Single-hex FEBio tests confirmed the Ogden side. A pressurised-panel test showed the bulge moves only by about the cube root of that. | Matching the fitted curve is not matching the law. Refit Marlow with an I1-only law (`Yeoh`, `scripts/fit_yeoh.py`) and check uniaxial, planar and equibiaxial stretch. Pick `k` for the working strain, not only from mu0. Also, a one-element shell test pulled only through its nodes reads 2-3x too soft (the back face lags; gotcha 24), so don't let a test-setup artifact pass as an element defect. |
| Audited the source connectors only for the part being debugged ("no connector to the LA is missing"), and kept blaming a compressed spring chain's buckling on the missing truss mass. | Asked which source structure a lofted fan stood in for, then listed what held each fan boundary node in every model version: the posterior-arcus fans had hung free from the vaginal wall since the tube they were lofted onto was replaced by a spring chain. That left 26 source connectors with no counterpart, and they pointed along the chain's buckling direction. | Audit connector families by both ends and name the FEBio construct carrying each one in the current version (`abaqus-inp-format.md`). When a chain buckles, split its drift along the directions of the supports the source gives it (`convergence-debugging.md`). Reattaching the fan moved the static wall from 20 % to 60 % load; the much softer source connectors alone did not. |
| Fitted one loft's material to its connectors and left the model's other lofts on the shared material they had always had. | Ran the same survey and strip fit for every loft (`loft_survey.py`, `loft_fit_all.py`). The shared material turned out to be an Abaqus rigid pipe beam's, with E scaled down and the beam's density kept. Against their own connectors the lofts ranged from 0.6x (too soft) to 10^7x too stiff, and in the runs they held every connector end within 1-2.5 mm, except the one loft already fitted. | A fix applied to one member of a family is a reason to audit the whole family. Check what each loft's material and density came from, not only its stiffness (`abaqus-inp-format.md`, lofts item 4). |
| Measured connector elongations at coordinate-matched nodes, and reported a 2.9 mm median for a loft that actually stretched 17-18 mm. | The same numbers for the connector-spring run looked implausibly different from the loft run. The lookup had returned an orphan duplicate at the Abaqus coordinate, which never moves. | When several nodes share a coordinate, read results at the one used by an element or spring (`geometry-cross-referencing.md` Rule 3). Cross-check one number against an independent run before building on it. |
| Generalised a validated fit tool and got a 1.44x different answer for the case it had been validated on. | Printed both tools' strip widths: the old spacing-based strips added up to 676 mm^2 for a 325 mm^2 loft. The old answer still matched the connectors in the running model (connector-end elongations), because a continuous sheet is stiffer than independent strips. | A strip-model fit is good to about +-50 %. The in-situ comparison against the exact alternative (connectors as springs) decides, not the fit's rms. Keep area-consistent widths and calibrate against that comparison. |
| Edited shared project files (READMEs, the next-session prompt) without checking whether another session was working on the same project. | A file edit was refused because the file had changed since it was read, and a Box folder appeared 2 s after a copy step. Another session had noticed the stopped run and done the same wrap-up. | Before editing shared files, list other sessions (e.g. ListAgents) and check the files' modification times. Treat an unexpected change as another writer and merge, don't overwrite. Copy with a refuse-if-exists check and verify with hashes. |
| Took the converted model's attachments as working because they looked attached: two lofts on `tied-node-on-facet`, a loft edge on a spring chain, and a midline 'held by its symmetry BC'. | The user saw scalloped gaps and a stiff-looking midline in FEBio Studio. Measured in the results: the ties (penalty 0.0005, a per-node N/mm spring) had let go by 2-5 mm, 8 loft edge nodes per side were never on the chain, and 328 zero-length ground springs (not in the source) held the midline in y and z while the BC only fixed x. | For every attachment, measure in the results how far the attached points drift apart. Check that a tie's penalty and any stand-in springs are plausible for the forces involved (`febio-xml-format.md` gotcha 17, `abaqus-inp-format.md` loft item 1 and the XSYMM note). |
| Carried `cutback 0.25` in every solver block for the whole project, and compared a test block's `cutback 0.5` against it, as if either did something. | A stalled run's failed-attempt times stepped down by a constant 0.000203 = dt0/21, not by halving. FEBio's source (`FETimeStepController::Retry()`) reads `cutback` only with `aggressiveness` 1. | Check a solver parameter is live before tuning or comparing it: read the retry times in the log, or the source. With `aggressiveness` 0 FEBio takes dt0/(max_retries + 1) off the step at each retry. |
| Kept `lstol` 0 (line search off) through most of the project because it had cured one stall in an early version of the model. | A small folding test the user had built earlier failed without the line search; one change in the full model then gave 6 failed attempts to full load instead of 99, with the same solution. | Re-test old convergence fixes after the model changes a lot. The line search also got a near-zero-loft variant past a wall where it had died at 27 % of load. |
| Fitted lofts to connectors and expected the fits to reproduce the connectors in situ wherever the strip fit was good. | The run with all 175 connectors as springs showed some connector ends *shortening* 4.7 mm (median) where the fitted loft held them to 1.1 mm. | A loft carries compression, and a connector table from (0, 0) with constant extrapolation is tension-only. Check the sign of the connector-end elongations in the spring run before fitting. No material fit can make a sheet slack in compression. |
| Left a loft edge pinned only at the source's point anchors (the connector origins), with free loft nodes between them on the same edge. | The user asked for the whole edge to be under the BC. Measured: with a weak fitted loft those nodes swung up to 3.6 mm (scalloping); with a stiff loft only 0.15 mm, so it had gone unnoticed. | Pin every loft node along an anchored edge. It gave the same solution with half the failed attempts, in two runs. Nodes held by almost nothing cost the solver even when they don't change the answer. |
| Offered a "more physical" material derivation (the total connector force over the loft's cross-section) as an improvement on the strip fit. | The in-situ check (connector-end elongations vs the connector run) showed it moved the ends further from the connectors. | Averaging strain over one mean length hides that a continuous loft strains its short part more. Judge any loft material by the in-situ check, not by how physical its derivation looks. |
| Read a 1 s dynamic run's states as the model's loaded response, and sized mass damping on a quasi-static speed estimate. | A 3 s ramp of the same model had 2.5x the LA displacement at the same load level; the freed vaginal wall moved at 100-200 mm/s, ~10x the estimate, so the damping visibly slowed the transient. | Compare a slower ramp (or a held load) at the same load before trusting dynamic numbers as the loaded state, and measure speeds before sizing damping. |
| Called a mass-damped run "the most stable version" and its t = 1 state the model's response at that load. | Holding the load for 1 s more, the LA grew 50 % and was still creeping. The source's truss chain (density 1e5 x tissue, a mass-scaling device) weighed 33 kg, and 329 kg on the screening base, against 70 g of tissue. C = 20/s on it was a drag about as large as the load. | Sum the mass per domain before using mass damping, and read a damped run as held back until a hold shows it has settled. Size C near 2 omega of the slow mode. |
| Screened supports, solver settings and damping one at a time on a stalled loft model, looking for the one change that would free it. | Every variant crawled at the same point. The failure locations kept naming the near-zero and P-arcus lofts. Replacing all the lofts by their source connectors passed with one failed attempt, and replacing only the soft ones reached full load too. | When one region leads the failure list in every variant, change that region, and test the source's own representation of it (the connectors) before tuning around it. |
| Removed a loft whose edge nodes an earlier fix had spliced into a spring chain, and ran the model. | 850 negative Jacobians in the first step at almost zero load. The per-element console report and a count of the nodes left only in springs found 16 massless, unsupported chain nodes. | Before removing a domain, list the nodes it leaves without an element or mass, and undo any splice made for it. A failure at zero load is a model defect, not physics. |
| Let a crawling run go on after a snap without looking at what had just changed. | Its fastest nodes (6 m/s) all sat next to a contact pair that had been open all run and had just touched at one facet. Without the pair it ran to t = 1 in 46 min; with a 10x softer penalty in 1 h 10. | After a snap, check which contact pairs have just closed. A contact onset at speed can stall an implicit run; soften the penalty and keep the pair. |
| Said the posterior-wall pressure pushed that wall onto the levator, from the load's name and the contact closing. | The user doubted it. The resultant direction (F = -p sum(n A)) showed that load pushing the wall away, and the nodal displacements showed the wall coming down with the anterior wall and the apex. | Compute a load's resultant direction, and check which side moved where a contact closed, before explaining a contact by a load. |
| Looked for what held a part's rotation among the springs on that part. | Their forces were a few N; the part (the perineal body) was placed by the wall it is fused to. Cutting one support family at a time on both lines found the lever two steps away: the posterior wall's lateral (paravaginal) connectors. Cut, the part turned 42 deg instead of 3; the part's own springs changed its descent, not its rotation. | To find what holds a body's rotation, first compute each attachment's moment per unit tension about the body's centroid (geometry only), then cut families one at a time, including the supports of whatever the body is fused to. Track the body's edges over time: here the front followed the wall and the back followed the levator. |
| Tuned the solver and the ties of the loft line when it crawled, because the fastest nodes sat at a loft tie. | Merging that tie and loosening dtol changed nothing; all J were 0.99-1.06 and the failed steps failed on the displacement norm with the energy converged. Swapping the anterior paravaginal lofts for their source connectors ran to full load with one failed attempt and matched the springs line within 2 deg. | A loft can carry compression and go floppy once a neighbouring support is weakened; a connector cannot. When only the loft version crawls, swap the lofts near the fastest nodes for their connectors as a test before tuning anything. |
| Screened a result that depends on timing (a part's rotation during loading) on the base with the truss chain's mass x10. | With the source chain mass the chains moved early, the levator hung from them descended early and dragged the part's back edge down: the base turned -7 deg instead of +3, the candidates ~6 deg less. The ranking held. | A mass-scaled support chain delays everything hung from it. Confirm any timing-dependent result, and every baseline, on the source mass before reporting a number. |
| Two long runs stopped mid-iteration (no error, no termination line, no crash event), and one was left unexplained for hours, as if the model had failed late in the hold. | Windows had 1.7 GB of committed memory left of ~100 GB while RAM was free: a result viewer open for a day held 53 GB of commit. Once its files were closed, the next run finished normally. | A log that simply stops is not a numerical failure. Check the commit charge and which process holds it before debugging the model, and before starting long runs. |
| Suspected the shell's thickness treatment (nodes on the top face in FEBio, the mid-surface in Abaqus) of a levator displacement ~3x larger than remembered from Abaqus. | A pinned-panel test put every treatment within 4 %. In the full model, mid-surface shells, the back face held at the pins and a doubled thickness moved the levator 8, 5 and 20 %. Splitting its displacement showed the tied edge moving as much as the rest: the levator hung on truss chains pinned only at their ends, which carried 60 % of its load. Such a chain sags with the square root of its stretch, so 10x stiffer chains lowered it only 8 %. | Before blaming an element formulation for a displacement gap, split the displacement into the supports' motion and the part's own deformation, and find which support carries the load. |
| Refit one Marlow material (the levator) after its uniaxial Ogden fit proved 2-3x soft in biaxial stretch, and left the other Marlow materials as the converter's Ogden fits. | A session later `fit_yeoh.py --ogden` showed the vaginal walls' fits 3x stiff at 20 % strain and 2.3x soft in equibiaxial stretch at 1.5, and the perineal body's 3-4x soft in uniaxial stretch. | When one converted hyperelastic law fails a stretch-state check, check them all: run `fit_yeoh.py --ogden` on every Marlow material and refit each to Yeoh. |
| Softened a contact penalty 10x to get past a stall at first touch, without finding why one touching facet stalled the run. | The per-facet contact pressure in the plot file showed the touch carried only by the two-pass second pass, at the edge row of the wall's contact surface; the edge nodes reversed direction every step at 2-10 m/s. `knmult 1`, a larger `search_tol`, `seg_up` and one pass did not help. It was a pinch: connectors at the edge tied the wall to a truss chain tied to the other surface and pulled the edge onto it; taking the 30 facets that hold connector ends out of the contact passed at the stiff penalty. | When a run stalls as a contact first touches, find which pass and which facets carry it, and whether they sit on the surface's boundary (convergence-debugging.md). |
| Compared the model for days with a remembered Abaqus displacement (the levator ~10 mm). | The source's paper reports no levator displacement. It does report POP-Q points for named impairment cases; reproducing one gave numbers to compare (posterior wall -0.8 vs +4 mm, anterior wall +13.3 vs below the hymen). | Compare against the source's published numbers: reproduce a published case and measure what the paper reports. |
| Waited for hours on one background waiter ("tell me when run X ends") while working unattended; X crawled for 7.5 h and six other crawling runs went unchecked. | Found only when the waiter returned 6.5 h later; the six had made almost no progress. An autostop that fires only on zero progress never stops a run creeping in tiny steps. | Cap every wait at ~30 min and re-check every run's rate (t gained per 30 min) each time. Stop crawlers that have answered their question. |
| Joined two separately meshed parts (a contact-only seam that stalled the solver) with a tie, then with springs, to make a softer, source-faithful material converge. | Every joint that converged also moved the results (one wall 11-14 mm higher), and in the source paper's impairment cases the other wall stopped responding to the impairment (Bp from case P1 to P2: +0.6 mm vs the paper's +5); joints soft enough to leave the results alone did not converge.
